Criando um aplicativo em Flutter para classificar imagens (gato e cachorro) com Teachable Machine (TensorFlow)

Notas de aula do prof. Kleber de Oliveira Andrade — edição revisada em novembro de 2026

Como transformar uma fotografia em uma previsão de gato ou cachorro? Nesta aula vamos percorrer o caminho completo: preparar classes no Teachable Machine, entender o arquivo exportado, tratar a imagem, executar inferência local e apresentar os dois scores em uma interface Flutter. O aplicativo continua usando o modelo original do projeto, agora com null safety, dependências atuais, validação de dados e uma plataforma de execução efetivamente verificada: macOS.

Você precisa conhecer o básico de Dart, funções assíncronas e widgets. Ao terminar, deverá conseguir explicar por que a orientação, o recorte, a normalização e a ordem dos rótulos fazem parte do modelo, e não são detalhes cosméticos da tela.

O que o modelo realmente responde

Um classificador aprende padrões a partir de exemplos rotulados. Depois do treino, a inferência aplica os pesos aprendidos a uma nova entrada. Nosso modelo só possui duas saídas: Gato e Cachorro. Por isso, uma cadeira também receberá scores para essas duas classes. Um score alto não comprova que exista um animal na foto e não equivale à acurácia do sistema.

A versão de 2020 apresentava percentuais obtidos durante um treinamento. Não temos aqui o conjunto de dados exato, sua divisão nem os parâmetros necessários para reproduzir esses números. Esta edição não os usa como promessa de desempenho. Vamos separar funcionamento do aplicativo, testes de duas amostras e avaliação de qualidade de um modelo.

Preparando seu próprio experimento no Teachable Machine

Abra Teachable Machine, crie um projeto de imagens padrão e nomeie as classes Gato e Cachorro, nessa ordem. Use imagens próprias ou com licença que permita o uso pretendido. Evite pessoas, documentos e dados pessoais. Registre origem e licença; poder baixar uma foto não significa ter permissão para redistribuí-la.

Colete diversidade de animais, fundos, posições e iluminação. Reserve imagens de animais diferentes para avaliação e mantenha-as fora do treino. Fotografias quase idênticas ou do mesmo animal em ambos os grupos podem produzir uma avaliação excessivamente otimista. Equilibre as classes e evite que o fundo seja o principal sinal para distinguir os animais.

Treine o modelo e observe as métricas de treino e validação. Uma perda de treino que melhora enquanto a validação piora pode indicar sobreajuste; não determine o número ideal de épocas a partir de um único gráfico antigo. Compare experiências registrando os parâmetros e os dados utilizados. Guarde uma cópia do projeto para poder continuar depois, sem compartilhar dados privados.

Exporte em TensorFlow Lite com ponto flutuante, preservando model_unquant.tflite e labels.txt do mesmo treino. O aplicativo desta aula exige duas classes e entrada RGB float32 de 224×224. Um modelo quantizado ou com outra dimensão precisa de mudanças no contrato, no pré-processamento e nos testes. Não basta renomear o arquivo. Para acompanhar esta edição, use primeiro os assets já incluídos no repositório; nenhum novo treino é necessário.

Ambiente e execução reproduzível

A revisão foi validada com Flutter 3.50.0 estável, Dart 3.14.0, Xcode 27.2 e CocoaPods 1.16.2. Instale a versão indicada no arquivo .flutter-version. O macOS 12 ou superior é a plataforma verificada. Android e iOS receberam configurações atuais, mas não há teste físico de câmera ou de aparelho nesta revisão. Nenhuma licença pendente do Android foi aceita automaticamente. O runtime nativo utilizado não oferece implementação web para este projeto.

git clone https://github.com/kleberandrade/teachable-ml-flutter.git
cd teachable-ml-flutter
flutter --version
flutter pub get --enforce-lockfile

Os comandos partem da raiz do repositório e usam o código completo. Não é necessário criar outro aplicativo vazio, configurar Firebase, obter credenciais ou hospedar o modelo. Depois da instalação, as fotos são processadas no próprio dispositivo.

Uma arquitetura pequena com responsabilidades claras

Em lib/domain/classification.dart ficam funções puras: leitura dos rótulos, validação do contrato, tratamento dos pixels e interpretação dos scores. Em lib/classifier.dart ficam o acesso ao asset e a chamada nativa. O controlador em lib/controller.dart coordena as operações e descarta resultados antigos. A interface e a integração com o seletor ficam em lib/main.dart. Assim conseguimos testar as regras sem câmera nem runtime e reservar o teste nativo para a integração real.

Os trechos a seguir foram extraídos dos fontes finais. São partes explicativas da implementação existente, não arquivos completos para substituir isoladamente. O repositório contém os imports, as classes e os testes necessários para executá-los.

Validando o contrato antes de inferir

A inspeção do FlatBuffer e do interpretador confirmou uma entrada float32 [1,224,224,3] e uma saída float32 [1,2]. O arquivo de rótulos contém 0 Gato e 1 Cachorro. A primeira dimensão representa o lote, as seguintes são altura, largura e canais RGB. O índice da saída deve continuar associado ao mesmo rótulo mesmo quando ordenamos os resultados na tela.

void validateContract(
  List<int> input,
  List<int> output,
  bool floatInput,
  bool floatOutput,
  int labelCount,
) {
  if (input.join(',') != '1,224,224,3' ||
      output.join(',') != '1,$labelCount' ||
      !floatInput ||
      !floatOutput) {
    throw const FormatException(
      'Modelo incompatível: esperado RGB float32 [1,224,224,3] → [1,2].',
    );
  }
}

parseLabels também rejeita índices fora de ordem, nomes vazios, duplicados e quantidade diferente de duas classes. Essa validação acontece na entrada do sistema. Se você exportar um novo modelo, mantenha os rótulos correspondentes e revise o contrato antes de alterar a interface.

Da fotografia aos pixels que o modelo espera

O pré-processamento limita o arquivo a 12 MB e a imagem a 24 megapixels. Verificamos as dimensões antes de decodificar o quadro inteiro, corrigimos a orientação EXIF, convertemos os canais para oito bits e fazemos um recorte quadrado central com redimensionamento para 224×224. A prévia mantém a proporção original; o modelo recebe o recorte quadrado. Posicione o animal no centro para reduzir perdas nesse recorte.

Float32List preprocess(Uint8List bytes) {
  if (bytes.isEmpty || bytes.length > maxImageBytes) {
    throw const FormatException('Escolha uma imagem de até 12 MB.');
  }
  final decoder = img.findDecoderForData(bytes);
  final info = decoder?.startDecode(bytes);
  if (info == null || info.width * info.height > 24000000) {
    throw const FormatException('Imagem inválida ou maior que 24 megapixels.');
  }
  final decoded = decoder!.decodeFrame(0);
  if (decoded == null) {
    throw const FormatException('Não foi possível abrir a imagem.');
  }
  final oriented = img
      .bakeOrientation(decoded)
      .convert(format: img.Format.uint8, numChannels: 3);
  final square = img.copyResizeCropSquare(
    oriented,
    size: inputSize,
    interpolation: img.Interpolation.linear,
  );
  final result = Float32List(inputSize * inputSize * 3);
  var index = 0;
  for (final pixel in square) {
    result[index++] = pixel.r / 127.5 - 1;
    result[index++] = pixel.g / 127.5 - 1;
    result[index++] = pixel.b / 127.5 - 1;
  }
  return result;
}

A normalização usada é (canal / 127.5) - 1: preto vira -1 e branco vira 1. Ela segue a convenção MobileNet do Teachable Machine. O helper antigo usava média zero e divisor 255, produzindo [0,1]. A dimensão de um tensor, sozinha, não informa a escala correta; por isso o contrato e a origem do modelo devem ser documentados. O grafo original começa com PAD e convoluções, sem uma etapa anterior de normalização. Como os metadados de treinamento não foram preservados, não afirmamos reproduzir todas as operações do treino histórico.

Executando o modelo sem travar a tela

LocalClassifier carrega o asset, confere as entradas e saídas e entrega cada imagem a um isolate. Cada trabalho cria e fecha seu próprio interpretador nativo, inclusive em caso de exceção. Isso evita compartilhar recursos mutáveis com uma tela que já foi descartada. Neste exemplo didático há um custo de criação por imagem; para uma câmera em fluxo contínuo seria preciso medir e projetar outro ciclo de vida.

List<Prediction> _infer((Uint8List, Uint8List, List<String>) request) {
  final (model, image, labels) = request;
  final pixels = preprocess(image);
  final interpreter = Interpreter.fromBuffer(model);
  try {
    _validate(interpreter, labels.length);
    final output = [List<double>.filled(labels.length, 0)];
    interpreter.run(pixels.buffer.asUint8List(), output);
    return interpret(output.single, labels);
  } finally {
    interpreter.close();
  }
}

No macOS, tool/embed_tflite_macos.sh é executado pela fase de build do Xcode para copiar e assinar a biblioteca incluída na versão travada de tflite_flutter. Ela não é baixada de um endereço aleatório durante a execução. O pacote ainda depende de CocoaPods nesse alvo e emite um aviso sobre a futura exigência de Swift Package Manager. O build local não é notarizado nem assinado para publicação na loja.

Interpretando resultados e recuperando falhas

A saída deve conter exatamente um score finito por classe, cada valor entre zero e um, com soma próxima de um. interpret valida essas condições e devolve Prediction(label, score) ordenado pelo score, sem trocar a associação entre índice e rótulo. Não filtramos a segunda classe com um limiar: as duas continuam visíveis para comparação.

List<Prediction> interpret(List<double> scores, List<String> labels) {
  if (scores.length != labels.length ||
      scores.isEmpty ||
      scores.any((s) => !s.isFinite || s < 0 || s > 1) ||
      (scores.fold(0.0, (a, b) => a + b) - 1).abs() > .01) {
    throw const FormatException('O modelo retornou probabilidades inválidas.');
  }
  return List.generate(scores.length, (i) => Prediction(labels[i], scores[i]))
    ..sort((a, b) => b.score.compareTo(a.score));
}

O controlador aguarda o carregamento do modelo antes de habilitar a seleção. Cancelar o seletor conserva o resultado anterior. Escolher outra imagem limpa os scores anteriores antes de analisar a nova entrada. Falhas de seleção, carregamento ou inferência produzem uma mensagem com recuperação. Recomeçar limpa imagem e scores; durante a análise, Cancelar análise invalida o resultado pendente. O trabalho isolado já iniciado pode terminar ao fundo, mas não atualiza uma tela reiniciada ou descartada.

Em Android, retrieveLostData recupera uma seleção quando o sistema destrói a Activity durante o seletor. Os botões de câmera aparecem apenas em Android/iOS. Permissões e funcionamento físico nesses sistemas precisam ser validados no aparelho; os testes deste projeto não substituem essa etapa. No macOS, o acesso é somente de leitura para o arquivo escolhido pelo usuário.

Testes, build e limites verificados

Os testes de domínio foram escritos antes da implementação e falharam pela ausência da nova API; depois passaram. O mesmo ciclo foi aplicado ao controlador e à substituição da interface. Nove testes de unidade/controlador/widget verificam rótulos, formas e tipos, normalização, orientação, scores inválidos, cancelamento, falhas, recuperação, descarte e layouts de 360×740 e 1200×800.

dart format --output=none --set-exit-if-changed lib test integration_test
flutter analyze
flutter test --coverage
flutter test integration_test/inference_test.dart -d macos
flutter build macos --release

O teste nativo carregou o modelo e classificou as duas fotos licenciadas: o gato teve Gato como maior score e o cachorro teve Cachorro. Também rejeitou uma entrada inválida. Dois exemplos não formam uma avaliação estatística. No aplicativo real foram verificados os exemplos, a abertura de arquivo pelo seletor, o cancelamento preservando o resultado e o reinício. Os builds debug e release passaram no macOS. A análise estática passou sem problemas. A automação do GitHub executa os mesmos checks e mantém seu status público no README.

Não declaramos teste físico de Android/iOS, de câmera ou de inferência no navegador. crapper, dryer e mutator instalados não suportam Dart; não há métricas inventadas dessas ferramentas. O objetivo é permitir que cada leitor diferencie o que foi executado, o que foi testado com dependências substituídas e o que ainda depende de validação na plataforma de destino.

Cinco exercícios práticos

  1. Dados com procedência. Objetivo: Montar um pequeno conjunto de avaliação independente do treino. Critério de conclusão: Reúna pelo menos dez imagens por classe com origem e licença registradas, sem dados pessoais. Entregue uma lista que demonstre a separação entre treino e avaliação e explique dois possíveis vieses.
  2. Contrato sob teste. Objetivo: Compreender a fronteira entre aplicativo e modelo. Critério de conclusão: Acrescente testes que rejeitem um tensor quantizado, um rótulo duplicado e uma saída de tamanho incorreto. Mostre cada falha esperada antes da correção e mantenha todos os testes passando.
  3. O efeito do recorte. Objetivo: Investigar como a entrada altera a previsão. Critério de conclusão: Compare pelo menos seis fotos centralizadas e deslocadas, registrando os dois scores e o recorte aplicado. Entregue uma explicação sobre diferenças sem chamar o score de acurácia.
  4. Recuperação acessível. Objetivo: Garantir que a interação seja utilizável após falhas. Critério de conclusão: Adicione um teste de widget para erro de inferência seguido de nova escolha bem-sucedida. Demonstre uso com teclado e texto ampliado sem overflow, incluindo a limpeza correta de resultados antigos.
  5. Novo treino e relatório. Objetivo: Avaliar um modelo próprio de duas classes mantendo o pipeline consistente. Critério de conclusão: Exporte seu modelo float32, atualize contrato e rótulos se necessário e execute os testes. Entregue um relatório de até duas páginas com versões, dados, matriz de confusão no conjunto separado, limitações e comparação com o modelo original. Não publique dados sem permissão.
